## Как выбирается уровень

| Уровень | Граница проверки |
|---|---|
| unit | Java-метод/объект без сети и настоящей БД; зависимости замоканы. Подходит для ветвления, арифметики, выбора BIN, вызова компенсации |
| api | HTTP-контракт одного сервиса или его HTTP-клиента: статус, JSON, путь, валидация. Зависимости заменены mock/stub, проверка состояния настоящей БД не входит в oracle |
| integration | Реальные PostgreSQL/AMQP, JPA, транзакции, блокировки, доставка; иногда несколько сервисов вокруг одного взаимодействия. Проверка SQL не становится unit из-за вызова Java-метода |
| e2e | Полный бизнес-путь от внешнего Gateway-входа до изменения денег и наблюдаемого публичного журнала; реальные внутренние сервисы |

HTTP сам по себе не определяет уровень: POST → GET с проверкой реального сохранения — integration; POST к MVC slice с mock сервиса — api. Два сценария e2e ниже проверяют сборку полного пути; ветки и границы внутри него проверяются дешевле.

## Общие условия новых кейсов

- Каждый integration/e2e запускается на изолированной тестовой БД/очередях; для каждого сценария — отдельная карта, UUID сообщения, STAN и RRN. Отказы брокера воспроизводятся только в этом стенде.
- Карта по умолчанию: BIN 400000, cardholderName=IVAN IVANOV, currencyCode=643, dailyLimit=5000000, monthlyLimit=10000000, initialBalance=1000000; статус ACTIVE; BIN предварительно присутствует в CMS. PAN берётся из ответа создания, не из случайного примера. День/месяц в limit_usage исходно не использованы.
- Все суммы — целое число копеек. HTTP AuthorizationRequest: mti=0100, stan=000301 (в следующих кейсах уникальный шестизначный), pan карты, processingCode=000000, amount=100000, currencyCode=643, transmissionDateTime — текущий Instant, terminalId=TERM0001, terminalType=POS, merchantId=MERCH00000000001 (15 символов), mcc=5411, acquirerId=ACQ001, issuerId=ISS001. При входе через Gateway issuerId назначит Switch. Все поля обязательны для прямого Authorization-вызова по [AuthorizationRequest.java](../../services/common/src/main/java/com/processing/common/dto/authorization/AuthorizationRequest.java).
- Для дат D берётся из transmissionDateTime в UTC. Для expiry-тестов относительные месяцы задаются относительно D; для генерации карты — относительно YearMonth.now(). Не переносить сентябрьские даты старых кейсов в октябрь без пересчёта.
- Для reserve тело содержит amount и уникальный 12-значный rrn; rollback — rrn, pan, amount. PAN в path и body совпадает.
- Eventual consistency: опрос каждые 100–250 ms до 10s. Это **тестовый бюджет ожидания**, не заявленный SLA. Фиксированный sleep и немедленный GET не заменяют ожидание условия.
- Logger ищется через GET /api/transactions/search?pan={pan}&status={status}&limit=50&offset=0; из ответа выбирается запись с нужным STAN/RRN. Сам STAN не является параметром фильтра в [TransactionFilter](../../services/transaction-logger/src/main/java/com/processing/transactionlogger/specification/TransactionFilter.java). Для тестов доставки проверяется UUID в БД.
- При работе с CMS напрямую исключается влияние Gateway response cache. В e2e контроль денег выполняется напрямую CMS/SQL после бизнес-запроса через Gateway.
- Для unit используются указанные DTO/доменные объекты; фикстуры не создаются через сеть. Для api запускается HTTP slice/локальный stub, а не весь Compose.

### Почему новые кейсы находятся именно на этих уровнях

| ID | Обоснование самого низкого адекватного уровня |
|---|---|
| P3-01 | Проверяется условие amount > 0 в чистом Validator; HTTP добавил бы лишние зависимости |
| P3-02, P3-03 | Маршрутизация — чтение Map и substring, БД/внешний BIN не участвуют |
| P3-04, P3-05 | Проверяется ветвление authorize и отсутствие вызовов нижних зависимостей; не корректность SQL |
| P3-06, P3-07 | Арифметика и защита перехода в immutable domain records, инфраструктуры нет |
| P3-08 | Нужны HTTP status и факт остановки до Switch; одного unit Validator недостаточно |
| P3-09 | Проверяется контроллерное преобразование бизнес-ответа в HTTP 403, а не логика сервиса |
| P3-10 | @Valid и exception handler работают на HTTP-границе; отсутствие вызова сервиса исключает запись |
| P3-11 | POST/PATCH/DELETE и последующий GET должны отражать реальную БД и soft delete |
| P3-12 | Условия ON CONFLICT и атомарное изменение проверяются настоящим PostgreSQL |
| P3-13 | PESSIMISTIC_WRITE и конкурирующие транзакции нельзя доказать mock repository |
| P3-14, P3-15 | Нужны AMQP-конвертация, доставка consumer и реальное сохранение/дедупликация |
| P3-16 | Счётчик попыток и выбор статуса находятся в processSingleEvent; broker для ветвления не нужен |
| P3-17 | Доказывается путь outbox → AMQP → Notification → БД после восстановления зависимости |
| P3-18 | Binding и TTL — поведение реального брокера; управление consumers изолирует его от retry |
| P3-19 | Нужны штатные контейнеры listener и брокер; ошибка БД моделируется, но retry-handler не заменяется тестовым |
| P3-20 | Требуется наблюдать реальные AMQP confirm; HTTP stub Authorization удерживает проверку ниже e2e |
| P3-21 | Проверяется только решение RouteService вызвать rollback по log=false; транспорт и денежный эффект отдельно |
| P3-22 | Возврат баланса в CMS и limit_usage в Authorization — межсервисная компенсация с реальной БД |
| P3-23, P3-24 | Проверяется полный путь через Gateway и публичное чтение журнала после изменения денег/статуса; это два контрольных сценария сборки системы |
| P3-25 | Реальный HTTP-клиент должен правильно обработать статус внешнего API; pure mock клиента это скроет |
| P3-26 | Rollback Spring-транзакции при ошибке outbox требует proxy и PostgreSQL |

### Покрытие обязательных путей

| Путь задания | Новые кейсы |
|---|---|
| Sync: валидация | P3-01, P3-08, P3-10 |
| Sync: BIN routing | P3-02, P3-03; HTTP BIN fallback — P3-25 |
| Sync: статус/баланс/лимиты | P3-04, P3-05, P3-06, P3-12 |
| Sync: CRUD и резервирование | P3-11, P3-13; повтор rollback — P3-07 |
| Async: Logger и eventual consistency | P3-14, P3-15, P3-23, P3-24 |
| Async: publisher-confirm + reversal | P3-20 (требование); P3-21 (имеющаяся оркестрация); P3-22 (полнота компенсации) |
| Async: outbox → Notification | P3-16, P3-17, P3-26 |
| Async: DLX/DLQ, retry, TTL | P3-18, P3-19 |

P3-19, P3-20 и P3-22 — нормативные тесты с ожидаемым расхождением по статическому анализу. Они остаются полноценными проверками требований, но не доказательством уже работающей функции. Конкретные результаты, задержки и сообщения об ошибках заполняются только после исполнения.

### Поправки к старым ожиданиям по текущему коду

Эта таблица обязательна при исполнении старых кейсов. Она отделяет исходный oracle из практики 2 от реализации; если oracle вытекает из ТЗ, расхождение оформляется как дефект, а не молча считается PASS.

| Кейсы / утверждение | Что выяснено по коду и как учитывать |
|---|---|
| AUTH-EC-04 | Недоступность CMS в [AuthServiceImpl.java](../../services/authorization/src/main/java/com/processing/authorization/services/AuthServiceImpl.java) → SERVICE_UNAVAILABLE / 96, а [AuthControllerImpl.java](../../services/authorization/src/main/java/com/processing/authorization/controller/AuthControllerImpl.java) → HTTP 503. Старые 05 / ISSUER_TIMEOUT не соответствуют этому пути; 05 при недоступности самого Authorization формирует Switch ([AuthorizationResponse.java](../../services/common/src/main/java/com/processing/common/dto/authorization/AuthorizationResponse.java)) |
| AUTH-PW-06 и AUTH-PW-20 | При недостаточном балансе и превышенных лимитах первым возвращается 51, не 61: баланс проверяется до SQL лимитов ([AuthServiceImpl.java](../../services/authorization/src/main/java/com/processing/authorization/services/AuthServiceImpl.java)). Для остальных комбинаций также соблюдать фактический приоритет |

Для исторических строк fixture должна согласованно заполнять оба поля |
| AUTH-EC-13 | Генерация RRN использует локальный синхронизированный счётчик блоков по 1000 значений и PostgreSQL rrn_seq ([AuthServiceImpl.java](../../services/authorization/src/main/java/com/processing/authorization/services/AuthServiceImpl.java), [LimitUsageRepository.java](../../services/authorization/src/main/java/com/processing/authorization/repositories/LimitUsageRepository.java)), а не только счётчик совпадений секунды |

Сентябрьские 0826/0926/1026 — фиксированная историческая фикстура; для проверки «предыдущий/текущий/следующий» в октябре нужны 0926/1026/1126 |
| CMS-EC-11 | [CardController.java](../../services/card-management/src/main/java/com/processing/cardmanagement/controllers/CardController.java) задаёт HTTP default limit=10; default 50 в [application.properties](../../services/card-management/src/main/resources/application.properties) действует при null на уровне сервиса, но контроллер подставляет 10. ### Фактические пропорции и объяснение отклонений

Получился **очень широкий интеграционный слой**, а не классическая 70/20/10 пирамида. Причина не только в микросервисной архитектуре: 93 унаследованных кейса были написаны как внешние сценарии HTTP с проверкой хранения. Сохранение их oracle требует реальной БД. Дополнительно лимиты реализованы native SQL, резервы защищены блокировками, outbox и consumers связывают несколько хранилищ — mock не проверяет эти свойства.

Новые кейсы более сбалансированы: 9/26 unit (34,62%), 15/26 api+integration (57,69%), 2/26 e2e (7,69%). Это не попытка подогнать общую долю: 26 новых проверок не должны скрывать стоимость 93 старых.

**Ice-cream cone по E2E нет:** полный контур используется лишь в 2 из 119 кейсов. Однако есть другой риск — медленные и сложные интеграционные тесты при недостатке дешёвых unit. В следующих модулях стоит выделить самостоятельные unit для формата PAN, выбора причины отказа и расчётов Card; потом пересмотреть дублирующие интеграционные комбинации, сохранив реальные SQL-границы и транзакционные проверки. В этой работе старые ID не удалены и не пересчитаны дважды.

**Дефицит API-контрактов нельзя оценивать одной суммой api/integration:** отдельно API всего 11/119 (9,24%). Новые проверки добавляют Gateway validation, HTTP-маппинг отказа Authorization, валидацию CMS и BIN fallback, но контракт комиссии Merchant и все response DTO этим набором не исчерпываются. Это зона дальнейшего расширения, а не утверждение о полном покрытии.

Количество тест-кейсов не равно проценту строк кода, числу запускаемых JUnit-методов или времени прогона. Например, один concurrency-кейс сложнее одного unit, а две итерации проверки двух DLQ не создают два новых ID. Нормативные P3-19/20/22 учитываются как спроектированные проверки, а не как успешные реализации.
