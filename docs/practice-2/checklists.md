# Чек-листы: дымовое тестирование и критический путь

Периферийные сервисы СМП проверяются по чек-листам; ядро (Authorization, Card-Management) покрыто в `test-design.md`. Дымовое тестирование выполняется после каждой сборки и является критерием входа (см. `test-plan.md`). Проверки критического пути перечислены по убыванию риска. Пункты отмечаются после прогона.

## Система целиком

### Дымовое тестирование

- [ ] `docker compose up` поднимает все сервисы; контейнеры в статусе healthy.
- [ ] Gateway `GET /health` показывает `ok` для Switch, Authorization, Card-Management и Logger.
- [ ] Одна валидная транзакция через Gateway получает ответ и появляется на Dashboard.

### Критический путь

- [ ] Одобренная транзакция проходит цепочку Terminal Simulator → Gateway → Switch → Authorization → CMS → RabbitMQ → Logger → WebSocket → Dashboard без потери и искажения данных.
- [ ] Баланс карты в CMS уменьшается ровно на сумму одобренной транзакции.
- [ ] Отклонённая транзакция сохраняется в журнале с причиной отказа; баланс не меняется.
- [ ] Один и тот же RRN одинаков в ответе клиенту, журнале Logger и на Dashboard.

## Gateway

Источник: [ТЗ](../../tz/02-gateway.md).

### Дымовое тестирование

- [ ] `:8080/health` отвечает 200; статусы downstream-сервисов доступны.
- [ ] `/docs` открывается; валидная транзакция на `POST /api/transactions` получает ответ.

### Критический путь

- [ ] Валидный запрос передаётся в Switch; ответ Switch возвращается клиенту без изменений.
- [ ] Отсутствие обязательного поля и нарушение каждого правила валидации (`mti`, `pan`, `amount`, `currencyCode`, `mcc`, `stan`) дают 400 `VALIDATION_ERROR` до передачи в Switch.
- [ ] Недоступный downstream-сервис даёт 503 `SERVICE_UNAVAILABLE` с `serviceName`.
- [ ] Более 100 запросов в секунду на `/api/transactions` дают 429 `RATE_LIMIT_EXCEEDED` с `retryAfterMs`.
- [ ] Пути `/api/cards/**`, `/api/transactions/search`, `/api/simulator/terminal/**`, `/api/simulator/merchant/**`, `/api/dashboard/**` проксируются в нужные сервисы.
- [ ] Каждый запрос логируется (метод, путь, статус, время); `X-Request-Id` присутствует в заголовках.

## Switch

Источник: [ТЗ](../../tz/03-switch.md).

### Дымовое тестирование

- [ ] `GET /health` отвечает 200; зависимость Authorization в статусе `ok`.
- [ ] `POST /api/internal/route` обрабатывает запрос с известным BIN.

### Критический путь

- [ ] Нет publisher confirm за 2 секунды для одобренной транзакции: выполняется reversal (`0400`), клиент получает `DECLINED/96`.
- [ ] Одобренная транзакция публикуется в `smp.transactions` с routing key `transaction.log` и подтверждением до ответа клиенту.
- [ ] BIN `400000`–`400004` определяют issuerId `ISS001`–`ISS005`; неизвестный BIN даёт `14` без вызова Authorization.
- [ ] Недоступный Authorization: три попытки, затем отказ `05`.
- [ ] Сообщение в журнал содержит исходный `mti` `0100`, сумму, RRN, issuerId и итоговый статус без искажений.
- [ ] Отклонённая транзакция при недоступном RabbitMQ возвращается клиенту с исходным ответом.

## Terminal Simulator

Источник: [ТЗ](../../tz/06-terminal-simulator.md).

### Дымовое тестирование

- [ ] `GET /health` отвечает 200.
- [ ] `POST /api/simulator/terminal/run` завершает короткий прогон `normal` и возвращает статистику.

### Критический путь

- [ ] Пул карт запрашивается через `GET /api/cards?limit=200`; транзакции отправляются через Gateway.
- [ ] `approved` + `declined` = `totalSubmitted`; итоги совпадают с полученными ответами.
- [ ] `declines_test` даёт пять групп по 20 %: `14`, CARD_BLOCKED, `51`, `61`, APPROVED.
- [ ] `normal`: только карты ACTIVE, суммы 100–5 000 ₽, время 09:00–22:00, MCC 5411.
- [ ] `mixed`, `high_value`, `night_time` соблюдают заданные доли, суммы и время.
- [ ] STAN — шесть цифр, растёт последовательно и после `999999` переходит к `000001`.

## Merchant / Acquirer Simulator

Источник: [ТЗ](../../tz/07-merchant-acquirer.md).

### Дымовое тестирование

- [ ] `GET /health` отвечает 200; `merchantsLoaded` не меньше 20.
- [ ] `POST /api/simulator/merchant/run` завершает короткий прогон `grocery`.

### Критический путь

- [ ] Комиссия эквайрера рассчитана в копейках по ставке мерчанта и сохранена в журнале.
- [ ] Комиссия не передаётся в AuthorizationRequest; merchantId и acquirerId соответствуют мерчанту.
- [ ] `grocery`, `electronics`, `restaurant`, `travel` используют MCC, суммы и время своего сценария.
- [ ] Явные `mccCodes` заменяют MCC сценария, сохраняя его диапазон сумм и времени.
- [ ] Итоги approved/declined совпадают с полученными ответами.

## Transaction Logger

Источник: [ТЗ](../../tz/08-transaction-logger.md).

### Дымовое тестирование

- [ ] `:8088/health` отвечает 200; `transactionsStored` возвращается.
- [ ] `GET /api/transactions/search` и `GET /api/dashboard/stats` отвечают; `/ws/transactions` принимает соединение.

### Критический путь

- [ ] Транзакции из очереди `transaction-log` сохраняются с исходными суммой, RRN, статусом и причиной отказа.
- [ ] `POST /api/internal/log` создаёт запись с 201; повтор с тем же `id` даёт 200 без дубликата.
- [ ] Новая транзакция приходит всем подключённым WebSocket-клиентам.
- [ ] Фильтры поиска сочетаются через AND; значения `limit` 50 и `offset` 0 по умолчанию; `total` корректен; пустая выборка возвращается без ошибки.
- [ ] Статистика совпадает с сохранёнными данными; `approvalRate` = approved / total.
- [ ] `GET /api/dashboard/recent` возвращает заданное число записей, последние первыми.

## Web Dashboard

Источник: [ТЗ](../../tz/09-web-dashboard.md).

### Дымовое тестирование

- [ ] Dashboard открывается; KPI, графики и таблица загружаются без ошибок.
- [ ] WebSocket к `ws://localhost:8088/ws/transactions` подключён; индикатор соединения зелёный.

### Критический путь

- [ ] Суммы переведены из копеек в рубли; KPI совпадают с `GET /api/dashboard/stats`.
- [ ] Новая транзакция появляется в начале таблицы и обновляет KPI, линейный и круговой графики без перезагрузки.
- [ ] PAN замаскирован: `4000****0001` в таблице, `400000****0001` в деталях; полный PAN нигде не отображается.
- [ ] Фильтры по статусу, датам, BIN/эмитенту и MCC корректно ограничивают выборку.
- [ ] Детали по клику относятся к выбранной транзакции и содержат все поля из ТЗ.
- [ ] После обрыва WebSocket индикатор становится красным; соединение восстанавливается автоматически.

## Bin Lookup

Источники: [ТЗ интеграции](../../tz/04-authorization.md), [API сервиса](../../services/bin-lookup/README.md).

### Дымовое тестирование

- [ ] `:8096/actuator/health` отвечает 200; известный BIN возвращает `issuerId`, `bankName`, `countryCode`.

### Критический путь

- [ ] BIN `400000`–`400004` возвращают правильные issuerId; неизвестный BIN даёт 404.
- [ ] При 5xx Authorization выполняет две повторные попытки.
- [ ] При недоступности или таймауте (3 с на подключение, 5 с на чтение) используется issuerId из таблицы Switch; авторизация продолжается.

## Notification Service

Источники: [ТЗ событий](../../tz/05-card-management.md), [API сервиса](../../services/notification-service/README.md).

### Дымовое тестирование

- [ ] `:8097/actuator/health` отвечает 200; `/api/notifications` возвращает список.

### Критический путь

- [ ] Создание, изменение и удаление карты доходят через outbox → `smp.card-events` → очередь `card-notifications`.
- [ ] События в `outbox_event` переходят из `PENDING` в `PROCESSED` после публикации.
- [ ] При недоступном RabbitMQ событие получает три попытки, затем статус `FAILED`; после восстановления новые события доставляются.
- [ ] Уведомления сохраняют тип, routing key `card.*` и данные исходного события.
- [ ] Список уведомлений и пагинация соответствуют сохранённым событиям.
